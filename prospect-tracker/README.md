# eephus.io

eephus.io is a baseball analytics site. It has a magazine-style home page,
long-form articles, the PROSPX prospect tracker (a consensus FV-based MiLB
prospect tracker with surplus-value analytics), CollegeSavant for amateur
hitters and pitchers, ten MLB modules (Franchise, Free Agency, Projections,
MLB Stats, Alchemy Lab, Trade Machine, Arbitration, Club Ledger, In-Game
Management and Hall of Fame), the Diamond pages (Fantasy and Sports Betting),
a glossary that carries each model's methodology and track record, forums, and
a development team page.

The site is plain static files. There is no JS framework and no bundler.
Every page except PROSPX and CollegeSavant is generated by `build_site.py`,
usually as a shell plus one module script under `assets/`. PROSPX is a single
self-contained `index.html` that reads generated JSON. The data comes from a
Python pipeline (`run_monthly.py`).

## Install

```bash
pip install -r requirements.txt
```

## Running the site

```bash
# 1. Build the editorial pages from content/
python build_site.py

# 2. Serve the whole site at the domain root
python -m http.server 8000
#    open http://localhost:8000/        (Home)
#         http://localhost:8000/prospx/ (PROSPX app)
```

Serve from the repository root so the root-absolute asset paths (`/data/`,
`/vendor/`, `/assets/`) resolve. Production serves the site at the
`eephus.io` root the same way.

### Run tests

```bash
python -m pytest -q
```

## Accounts, profiles and forums

The account layer is optional: email accounts, profiles with favorites and
badges, a watchlist, forums and comments (voting, @mentions, sanitized
markdown, embedded PROSPX data), and notifications. Without Supabase config
the layer is inert and the site behaves as before, logged out, with the
localStorage watchlist still working.

Client assets, loaded on every page after `site.css`:

- `assets/eephus-account.js`: the only boundary to Supabase (auth, profiles,
  favorites, watchlist, threads, comments, votes, notifications, moderation).
  Injects the Supabase SDK only when configured; otherwise a no-op.
- `assets/eephus-ui.js`: the UI (nav account control, auth modal, onboarding,
  user flair, the forum component, homepage Forums module, notification
  center, moderation view). Falls back to a labeled local PREVIEW mode when
  unconfigured, so the forum renders without a backend.
- `assets/eephus-account.css`: styles. Circular avatars are the one exception
  to the site-wide sharp-corner rule.

The PROSPX app exposes a read-only `window.PROSPX` shim so the forum reuses
`headshotURL`, `teamLogoURL`, `formatMetric`, and the prospect index for
flair, embeds, and search.

Backend provisioning is in [`supabase/README.md`](supabase/README.md). Short
version:

- Auth: first-party email + password only, no social OAuth. Email
  verification and password reset on; optional magic-link sign-in.
- Database: Supabase Postgres for user data, with Row-Level Security on every
  table. SQLite (`prospects.db`) stays the build-time prospect store; the
  browser never touches it.
- Email: dev uses Supabase's built-in sender; production points Auth at
  Resend over SMTP. Set SPF/DKIM/DMARC on the domain.
- Migrations, in order: `0001` accounts/forums schema + RLS + triggers,
  `0002` avatars storage bucket, `0003` moderation (ban/suspend, rate
  limits, new-account reputation gates).

Front-end config: copy `assets/eephus-config.example.js` to
`assets/eephus-config.js` (git-ignored) and fill in the project URL and anon
key. The anon key is safe in the browser; RLS guards the data. If the file is
absent the account layer stays dormant.

Pipeline env vars (server-side only):

| Var | Where | Purpose |
|---|---|---|
| `SUPABASE_URL` | CI / local | project URL for `forum_notify.py` |
| `SUPABASE_SERVICE_ROLE_KEY` | CI secret only | insert FV-change notifications |

After the monthly grade refresh, `forum_notify.py` diffs each prospect's
consensus FV from `data/timeseries.json` and notifies users who watch a moved
prospect. It is a no-op without the env vars and runs as a continue-on-error
step in `.github/workflows/monthly.yml`.

```bash
# Preview the account/forum layer locally with no backend (PREVIEW mode):
python build_site.py && python -m http.server 8000

# Dry-run the FV-change notifier (no inserts):
python forum_notify.py --dry-run
```

## Adding an article

Articles are Markdown files. No code changes needed.

1. Create `content/articles/<slug>.md` with frontmatter:

   ```markdown
   ---
   title: My Headline
   author: Jane Doe
   handle: janedoe          # X/Twitter handle (optional)
   date: 2026-06-05         # YYYY-MM-DD, drives ordering (newest first)
   summary: One or two sentences shown on the card and as the article dek.
   ---

   Body in Markdown. Paragraphs, **bold**, *italic*, links, lists, and
   headings all work.

   Embed a YouTube clip on its own line:

   @youtube: https://youtu.be/VIDEO_ID
   ```

2. Re-run `python build_site.py`. This regenerates `/articles/` and writes
   `/articles/<slug>/index.html`.

## The data pipeline (`run_monthly.py`)

`run_monthly.py` is the data pipeline for PROSPX, independent of the site
build. It scrapes the public sources, ingests the hand-maintained rankings in
`data/manual_rankings.csv`, rebuilds the SQLite cache (`prospects.db`), and
exports the JSON the PROSPX app reads (`data/timeseries.json` plus the lazy
sidecars: graduates, inactive, rosters by org, draft, overseas, IFA).

### Two cadences

| Command | Cadence | Refreshes |
|---|---|---|
| `python run_monthly.py` | monthly | Consensus FV and per-source grades, tool grades, Arkmetrics (WAG, DvM+, RPS+, SC+, ToolDvM+), farm grades, the full ranking, the source-vs-source backtest, and the monthly board snapshot. Also everything the daily job does. |
| `python run_monthly.py --daily` | daily | Fast-moving data only: the TJStats and MLB Pipeline live boards, transactions, IL stints, roster status, debuts and graduations, promotions/demotions, and trades. Then rebuilds `data/timeseries.json` with no scrape and no re-grading. |

The two jobs write disjoint tables and are individually idempotent, so they
never conflict. The export stamps a `data_freshness` block into
`timeseries.json`: `grades_updated_at` is the last monthly run,
`transactions_updated_at` the last run of any kind. The Transactions and
Injured-List sections show an "updated daily, as of ..." stamp; the graded
board reflects its monthly cadence.

```bash
python run_monthly.py                 # full monthly refresh
python run_monthly.py --daily         # daily fast-moving refresh
python run_monthly.py --rebuild-only  # no scrape; re-ingest DB + re-export JSON
python run_monthly.py --skip-stats    # skip MLB / MiLB stat fetches
python run_monthly.py --force         # bypass HTTP + DB freshness cache
python run_monthly.py --dry-run       # diagnostic; no DB writes, no export
python run_monthly.py --workers 8     # cap thread-pool size
python run_monthly.py --out-dir path  # write data/*.json elsewhere
```

A data refresh does not require a site rebuild (PROSPX reads the JSON at
runtime), but running `build_site.py` afterward is harmless.

### Scheduling (GitHub Actions)

Two workflows run the cadences, both with a manual "Run workflow" button:

- `.github/workflows/daily.yml`: `run_monthly.py --daily`, 08:10 UTC daily.
- `.github/workflows/monthly.yml`: `run_monthly.py`, 10:00 UTC on the 1st.

They share a concurrency group so they never overlap and use a rolling
`actions/cache` for `prospects.db` and the HTTP cache. For a durable
production DB, point the cache step at a real state store (the workflow
comments mark where).

### History snapshots

Each run snapshots derived state: `metric_snapshots` (board rank, consensus
FV, and the Arkmetric family per month, which powers the Time Machine) and
`il_history` (an append-only IL timeline). `source_backtest.py` writes
`data/source_backtest.json` (the Methodology and Track Record tab) each
monthly run.

### Live source captures (TJStats, MLB Pipeline)

Two sources update between monthly grade releases, so the daily job captures
their current boards as date-stamped point-in-time rows:

- TJStats (`tjstats.py`): the page is a React front-end over a public
  WordPress REST API, so we read the JSON directly. The join key is the
  MLBAM id. The Live board carries FV and 20-80 tool grades and lands in the
  shared `snapshots` table (feeding present-day consensus) plus the
  `tjstats_snapshots` sidecar. Named historical boards land in the sidecar
  only, so historical TJStats data can never move present-day consensus.
  Identifying User-Agent, response cache, throttle, retries; a health check
  probes every endpoint's shape and skips the write on a malformed payload.
- MLB Pipeline (`scrapers.run_mlb_pipeline_live`): the monthly scrape writes
  each year's Top 100 to one fixed preseason interval, so in-season re-ranks
  would overwrite that single point. The daily capture force-fetches the
  current page and writes a date-stamped interval behind a parse-health gate
  (`validate_pipeline_live_board`): fewer than 90 rows, duplicate ranks, low
  FV or org coverage, or unresolved names skip the write.

Same-day re-runs of either capture update in place; a new day creates a new
point-in-time row. Backtests key on the earliest same-year snapshot, which
remains the preseason archive page, so vintage discipline holds.

`tjstats.compute_snapshot_diff(older, newer)` yields rank/FV deltas and
entries/exits between any two stored snapshots. Not yet surfaced in the UI.

## PROSPX views

Beyond the prospect board, PROSPX includes:

- Time Machine (`#tab=timemachine`): view the consensus board at any past
  snapshot, or diff two dates for a changelog of risers, fallers, new
  entries, graduates, and grade changes. URL-shareable.
- Scatterplots (`#tab=charts`): a configurable plot builder with any X/Y
  metric, color and size encodings, log scales, org/level/pos and threshold
  filters, brush-to-zoom, highlight/search, shareable URL config, and a
  Generate GFX export.
- Methodology and Track Record (in `/glossary/`): plain-language derivations
  of consensus FV and each Arkmetric, the source-vs-source backtest with
  sample-size and survivorship caveats, and the model accountability
  registry.
- Per-prospect detail pages add a per-source FV overlay on the FV history
  chart.

### Displayed metric: WAR / WAG / FV

A player's headline value slot escalates with on-field information, enforced
by one shared helper (`display_metric_for` in `build_site.py`; its JS mirror
`displayMetricFor` in `prospx/index.html` - keep the two in sync):

- Graduated to MLB: WAR (career eWAR since debut, plus WAR/yr). eWAR is the
  served WAR series from the 2026-09 epoch: Baseball-Reference run frame with
  pitching re-priced on FIP; fielding unchanged pending SDR; position players
  match bWAR today (glossary entry `ewar`). New debuts
  with no WAR posted yet show "WAR pending" rather than a fabricated number.
- Prospect with a settled sample: WAG (WAR Above Grade).
- Prospect with no meaningful sample: FV.

WAG is never shown on a sub-threshold sample. The gate is the WAG model's own
`below_meaningful_exposure` flag (`value_framework_config.yaml`,
`wag.meaningful_exposure`: 200 PA / 80 IP, about a third of a season), so
display and methodology can't drift.

### Overseas resilience

The Overseas section reads `data/overseas_timeseries.json`. Two guards keep
the section from silently emptying under the concurrent monthly pipeline:
storage loaders don't turn a transient "database is locked" into an empty
result, and `export_overseas_json` refuses to overwrite a known-good sidecar
with zero prospects while `overseas_snapshots` is non-empty.
`test_overseas_regression.py` covers both.

## Deploy

The build output is static files, so it deploys to any static host:

```bash
python run_monthly.py          # monthly: refresh grades + data/*.json
python run_monthly.py --daily  # daily: transactions / IL / roster / debuts / trades
python build_site.py           # regenerate the editorial pages
# then publish the repository contents (served at the domain root)
```

Publish `index.html`, `articles/`, `prospx/`, `fa/`, `projections/`,
`glossary/`, `forums/`, `team/`, `assets/`, `data/`, and `vendor/`. The site
must be served at the domain root so the root-absolute asset paths work.

The port to git.eephus.io is deferred by the owner. Its checklist is
[`docs/LAUNCH_READINESS.md`](docs/LAUNCH_READINESS.md) and its spec is
[`docs/port/PORT_SPEC.md`](docs/port/PORT_SPEC.md). The Beta checklist and review
queue are archived under `docs/archive/`.
