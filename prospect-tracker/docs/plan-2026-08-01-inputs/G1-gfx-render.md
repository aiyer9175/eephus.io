# LANE G1: Generate-GFX Top-100 board renderer — verified map

## 0. Two separate GFX systems; the Top-100 board lives in PROSPX, not the shared engine

There are TWO Generate-GFX systems (documented at `prospect-tracker/docs/generate-gfx.md:1-10`):

1. **PROSPX in-page engine** — all code inline in `prospect-tracker/prospx/index.html` (54,870 lines). DOM board built as HTML, rasterized by **html2canvas**. **This is the Top-100 prospects board renderer.** prospx/index.html does NOT load `assets/eephus-gfx.js` (grep confirms zero matches).
2. **Shared `EEPHUS_GFX`** — `prospect-tracker/assets/eephus-gfx.js` (788 lines), canvas-native (`renderBoard` at eephus-gfx.js:122). Loaded by FA, Projections, MLB Stats, PAL, Trade Machine, CollegeSavant, Fantasy, Glossary, News (version stamp `_GFX_VER` at `build_site.py:72`; script tags injected at `build_site.py:1722, 2772, 2903, 2933, 2984, 3034, 3079, 3196`; static copies e.g. `fa/index.html:34`, `news/index.html:129`). It never renders the PROSPX Top-100.

The "Top 100" image is simply the PROSPX **Prospects list board** (`kind:"prospect"`, section `"active"`) with the modal's Show control set to "Top 100".

## 1. Entry points and pipeline (PROSPX engine)

- **Snapshot**: each list render stores the exact filtered+sorted array. Active board: `renderActives()` → `_gfxSet("active", "prospect", filtered, {})` at prospx/index.html:17429. `_gfxSet` definition at :33250-33253 (`_gfxSnapshot = { section, kind, items, total, meta }`).
- **Trigger**: per-list "Generate GFX" buttons injected once at boot by `_gfxInjectListButtons()` (:35386-35399) into every `.filter-toggle-row` (+ spotlights/ifa/watchlist bars); invoked from boot at :54724-54725. Delegated click handler at :35297-35320: `.gfx-list-btn`/`.gfx-card-btn` → `openGfxModal()` (:35306).
- **Modal**: static markup `#gfx-overlay` at :8665-8741. `openGfxModal()` (:35031): list boards default `_gfxOpts.format = "wide"` (:35043), saves/forces theme, lazy-loads qrcode vendor, then `_gfxRefresh()`.
- **Mode selection**: `buildGfxBoard()` (:34817) branches on `_gfxSnapshot.kind` — `"prospect-card"` → `buildProspectCard` (:34011), `"farm-card"` → `buildFarmCard` (:34485), `"compare-card"` → `buildCompareCard` (:34674); everything else (including `"prospect"`) falls through to the list-board path. Row rendering is per-kind inside `_gfxRow(item, kind, meta)` (:33454).
- **Canvas creation/export**: the board is a detached `<div>` (created :34828) inserted into `#gfx-preview` and fit-scaled via CSS transform (`_gfxRefresh` :34949-34977). Export strips the transform and calls `exportElementAsImage(el, { scale: 2 })` (`_gfxCanvas` :35076-35082). `exportElementAsImage` (:33118-33151) lazy-injects `/vendor/html2canvas.min.js?v=20260709` (:33109-33112), awaits fonts + every `<img>` AND `background-image:url()` asset via `_gfxAwaitAssets` (:33049-33085, 8s per-asset timeout), then `html2canvas(el, { scale, backgroundColor, useCORS: true, logging: false, imageTimeout: 15000 })` with one retry.
- **Blob/actions**: `_gfxPrepareBlob` (:35098-35113) caches `canvas.toBlob(..., "image/png")` keyed by `_gfxConfigSig()` (:35090-35094). `downloadGfx` (:35170, anchor-click via `_gfxSaveBlob` :35157), `copyGfx` (:35201, ClipboardItem), `shareGfx` (:35184, Web Share files API), `animateGfx` (:35245, MediaRecorder WebM foil shimmer; support gate :35237). Filename from title: `_gfxFilename()` :35142-35146.
- **Pixel dimensions / DPR**: formats in `_GFX_FORMATS` (:33260-33266): portrait 1080x1350, tall 1080x1620, square 1080x1080, story 1080x1920, **wide 1600x900 (list default)**. These are CSS-pixel canvas sizes; the format pins `min-height` only — long lists extend taller (comment + code :34907-34910). Export is always html2canvas `scale: 2` (fixed supersample, NOT `devicePixelRatio`-dependent; `opts.scale || 2` at :33127), so a wide Top-100 PNG ships at 3200 x (2 x actual height). At 100 rows the board is taller than 900 logical px (see geometry below), so the exported Top-100 is ~3200 x ~3800+, not 3200x1800.

## 3. Surplus and $DvM+ provenance

- **Surplus $** (chip value line 1): `displaySurplusMM(p)` (:22406-22410) — returns `getEfv(p).surplus_mm` when eFV is the lead grade (from **`data/xfv.json`**, loaded :30994, keyed lookup `getEfv` :31021-31031), else `playerSurplusMM(p)` (:22395-22400) — baked `p.surplus.value_mm` from the timeseries payload, client `estimateSurplusValueMM` only as last-ditch fallback.
- **$DvM+** (chip value line 2): field `p.dollar_dvm_plus` on the active-prospect payload. Producer: `storage.py` — computed in the league pre-pass at storage.py:10703-10782 ("**$DvM+ (Surplus Development vs Mean)** — Per-prospect SURPLUS-VALUE DEVELOPMENT TRAJECTORY, indexed against the mean prospect at the SAME FV tier (100 = tier mean, +10 = 1σ better)"; trajectory = eFV/consensus grade-movement rate per year + 0.5 x age-vs-level term; z-scored within eFV tier, tiers <4 members borrow global spread; published unclamped `round(100.0 + 10.0*_z, 1)` at storage.py:10782 — a former `max(40, min(160, ...))` clamp was removed 2026-07-29). Stamped onto each serialized active at storage.py:14786-14790. The ORG-level roll-up is separate: `fin_dollar_dvm` leaf = mean of member prospects' values (`round(sum(_v)/len(_v), 1)` at storage.py:12083). Listed as an Arkmetric snapshot payload key at storage.py:3853 (`"dollar_dvm_plus", # $DvM+`).
- **What $DvM stands for**: "Surplus-Development index / Development vs Mean". Player-level tooltip text at prospx/index.html:35657-35659 (`dollarDvmTooltip`); the GFX footer legend (:33723) says "surplus-development index (100 = FV-tier avg)". Glossary: `dvm_plus` id = **farm-system** "DvM+ — Development vs Mean" (data/glossary.json: "Farm-system development index; 100 = league-mean FV growth. Drives the Development component of the farm report card"); org roll-up id `fin_dollar_dvm` = "Org $DvM+ … development of surplus dollars". **There is NO glossary entry for the per-player $DvM+** (see Defects).

## Defects found

1. **Glossary id collision / missing player-level $DvM+ entry.** The PROSPX leaderboard stat key `dvm_plus` (prospx/index.html:18124: `dvm_plus: { label: "$DvM+", ... getter: p => ... p.dollar_dvm_plus ... }`; chip at :9800 titled "$DvM+ - surplus-development index (100 = FV-tier average).") reads the **per-player** `dollar_dvm_plus`, but `data/glossary.json` id `dvm_plus` is defined as the **farm-system** "DvM+ — Development vs Mean … Drives the Development component of the farm report card". No glossary entry exists for the per-player $DvM+ (only org-level `fin_dollar_dvm` "Org $DvM+", plus tool-level `tools_dvm_plus`/`tool_specific_dvm_plus`). Any glossary-keyed tooltip or lookup on `dvm_plus`/"$DvM+" resolves to the wrong (farm) definition. The homepage teaser at build_site.py:1777 also pairs `("dvm_plus", "DvM+", "development vs. mean")` — the farm sense — while PROSPX surfaces the same key as the player $ metric.
2. **Inconsistent unknown-format fallbacks.** `buildGfxBoard` falls back to portrait (`_GFX_FORMATS[_gfxOpts.format] || _GFX_FORMATS.portrait`, :34826) while `_gfxColumnCount` falls back to wide (:34806). If `_gfxOpts.format` ever holds an unknown key, the board is laid out 1080px wide but columns are computed for 1600px (4 columns at MIN_COL_W 360 cannot fit in 1080). Latent today (the select only offers valid keys) but a real trap for any plan adding a format/preset.
3. **Dead/misleading return fields in the card-pack branch.** `buildGfxBoard`'s pack branch returns `h: board.offsetHeight || H` (:34859) but the board is not yet attached to the DOM, so `offsetHeight` is always 0 and `h` is always `H`; `w`/`h` returns are unused by the only caller `_gfxRefresh` (:34957 destructures `{ board, total }`). Harmless but misleading — a plan wiring new size presets must not trust these.
4. **`_gradePrimary()` conflates "any non-FV sort" with eFV-lead** (:32421: `return (typeof state !== "undefined" && state.sort === "fv") ? "fv" : "xfv";`). The GFX badge legend and surplus source (via `displaySurplusMM` :22408) therefore claim eFV-lead for e.g. age or Statcast+ sorts. Consistent between badge and legend (both use the same helper), so not a display contradiction, but a semantic wrinkle a plan touching the legend should know.
5. **Ecosystem note (adjacent, trusted context):** the GFX board's eFV surplus comes from `data/xfv.json` (:30994) and the known-open P0 (efv_score.py:2066 inside `run_backgrade` (def :1966): `factors = _relabel_pace_factor(factors, r.get("milb"))` references `r`, undefined in a loop whose vars are `rec`/`row` → NameError whenever `row.get("milb")` is truthy, killing the eFV regen tail) plus the nightly-monthly-skips-efv_export gotcha mean a regen can leave xfv.json stale — the Top-100 GFX would then silently export stale eFV badges/surplus while the consensus-side fields (from the timeseries payload) are fresh. No GFX-side staleness indicator exists (the header "as of" date reads `DATA.generated_at`, :33779 — the timeseries artifact, not xfv.json's vintage).
