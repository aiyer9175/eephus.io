# Decision Ledger

Consequential choices made while building the Phase 1 pilot, in the order they came up.

1. **Real Eephus champion-benchmark values are deferred, not fabricated.** The private source directories `milb-projections/` was built to export from (`~/pitcher_ewar`, `~/milb_pitcher_ewar`, `~/milb_park_rebuild`, `~/career_outcome_plus`) do not exist on this machine (checked: home directory, `eephus.io`'s sibling directories, depth 6 — nothing found). This pilot proceeds schema-only, using `milb-projections/fixtures/` for structure where relevant, and explicitly flags every point a real benchmark value would be needed. Real integration is a documented next step, contingent on the private exports being supplied later (either by running `milb-projections/adapters/*.py` against the real source paths, or by the exports being handed over directly).

2. **Sampling is stratified by venue within level, not just by level.** A one-game-per-level sanity probe (see `PILOT_SCOPE.md`) showed 100% pitch-tracking coverage at the sampled AAA and Low-A venues and 0% at the sampled AA and High-A venues — the opposite of a clean "AAA good, lower levels worse" gradient. A level-only sample would average this into a misleading fractional number per level. Venue-level stratification is the only way to actually test whether coverage is a level property, a venue/tracking-install property, or both, rather than assuming the answer.

3. **Season chosen: 2025, not 2026.** 2026 is in progress as of this research (today: 2026-07-19); using an incomplete season would bias any within-season "did coverage change" comparison and undercount games per venue for levels/parks with fewer scheduled dates so far. 2025 is the most recent fully completed season.

4. **Raw pulled data is cached locally but never committed.** Consistent with `milb-projections/`'s own reasoning for using JSON over CSV/Parquet (`eephus.io`'s `.gitignore` excludes both globally) — but raw per-game API responses are large, numerous (~300-360 files), fully public, and trivially regenerable from `scripts/`. Committing them would bloat git history for no benefit; a scoped `.gitignore` entry (`milb-pitch-quality-research/data_cache/`) keeps them out entirely. Only the aggregated matrix outputs (small, derived, and the actual research product) are committed.

5. **New sibling directory, not built inside `milb-projections/`.** `milb-projections/`'s own `ARCHITECTURE.md` documents it as additive and read-only with respect to Eephus, with "no consumers inside Eephus itself." Building the actual research inside it would blur a boundary that package's own docs go out of their way to establish. `milb-pitch-quality-research/` is a new, separate directory at the same level.

6. **No push to any remote at any point**, matching the standing precedent in `milb-projections/DECISION_LEDGER.md` #11 — pushing to a shared remote requires separate, explicit confirmation at the time of the request.

7. **Level scope: AAA/AA/High-A/Low-A only, no CPX/DSL.** Matches `milb-projections/manifests/BENCHMARK_MANIFEST.yaml`'s own scope (CPX/DSL have no dedicated pitcher-eWAR artifact in Eephus, so there would be nothing to eventually benchmark against even if coverage there turned out to be good).

## Phase 1B (identifiability, information content, noise isolation)

8. **A new team/venue-stratified sample replaces Phase 1A's venue-coverage sample for reliability work, without deleting it.** Phase 1A's sample (3 games/venue) was built to answer a coverage question and answered it well, but gives a median of ~39 pitches/pitcher — far short of what split-half/month-to-month reliability needs. Rather than modify Phase 1A's sample or scripts, Phase 1B adds a new, additive sample (`data_cache/samples/{level}_team_stratified.json`, `scripts/phase1b/sample_team_stratified.py`) written to the same `data_cache/{level}/{gamePk}.json` cache, so games already pulled in Phase 1A are automatically reused, not re-fetched.

9. **AAA/AA/High-A use team-stratified sampling (10 teams, ~30 games/team, home+away pooled); Low-A uses venue-stratified sampling deepened to the 10 already-confirmed-tracked venues, not a team sample.** Coverage is uniform-or-absent across whole levels for AAA/AA/High-A, so "team" is the natural unit for pooling one pitching staff's full workload. Low-A's tracked venues are shared by multiple franchises (they're Florida spring-training complexes hosting more than one FSL club) — discovered while building the sampler, not assumed going in — so "team" isn't a clean unit there; the venue itself, deepened from Phase 1A's 3 games to ~30, is the correct unit. This is a deviation from the original plan's "10 already-identified tracked teams" framing for Low-A, corrected once the team/venue overlap was found.

10. **Variance decomposition uses method-of-moments one-way/nested random-effects ANOVA, not a mixed-effects modeling library.** `statsmodels` is not installed in this environment; the classical Searle et al. unbalanced-ANOVA variance-component estimator (implemented directly in `scripts/phase1b/variance_decomposition.py`) requires no dependency beyond numpy/pandas and is standard, well-understood math — adequate given the charter's own framing of this deliverable as "understanding where information lives," not a precision estimate. A real bug was caught and fixed during development (the first nested pitcher×pitch-family implementation produced a variance in the wrong units — a mean-square without the average-group-size correction applied — caught by a sanity check against the expected physical scale before being used in any report).

11. **`ALL_LEVELS` vs. `TRACKED_ONLY` metric scoping is a hard architectural boundary, not a soft preference.** Confirmed directly (not assumed) that pitch-type identity itself (`details.type.code`), not just velocity/movement/spin, is absent at untracked venues — meaning no metric requiring pitch-type can ever be computed outcome-only. Every metric definition in `scripts/phase1b/metrics.py` is tagged with this scope, and every downstream script/report respects it rather than silently producing near-empty or misleading results for out-of-scope level/metric combinations.

12. **Promotion-seam analysis is explicitly labeled exploratory, using chronological (not hierarchical) level ordering.** "Which level came first" for a given pitcher is used only as a timestamp-ordering, not a confirmed promotion — the public schedule/feed data doesn't distinguish a promotion from a demotion, option, or rehab assignment. Reported transition counts (e.g. `AAA->AA`, not just `AA->AAA`) are shown in the output specifically so this ambiguity isn't hidden by the framing.

13. **`reports/phase1b/` and `scripts/phase1b/` subdirectories, not flat/prefixed files.** Nine new report deliverables plus five new scripts would otherwise clutter Phase 1A's existing flat `reports/`/`scripts/` structure; a subdirectory keeps the two phases' outputs cleanly separable while both phases' scripts still share `scripts/common.py` (via a `sys.path.insert` one level up).

## Phase 1C (incremental information, feature attribution, architecture finalization)

14. **No new API pull for Phase 1C.** The charter explicitly instructs against repeating coverage/trust/missingness/reliability/stabilization/identifiability/variance work — this phase reuses the exact games Phase 1B already cached (`data_cache/{level}/{gamePk}.json`), re-parsed rather than re-fetched.

15. **A new `pitch_dataset_v2.parquet` extends, rather than overwrites, Phase 1B's `pitch_dataset.parquet`.** The only real gap Phase 1C needed to close was `hitData` (weak contact/ground-ball/damage fields) — confirmed present at tracked venues since Phase 1A, but never extracted in Phase 1B (`FEATURE_FEASIBILITY_MATRIX.md` flagged this explicitly). Writing a new file rather than modifying Phase 1B's keeps that phase's reported numbers reproducible from the exact artifact they were computed against.

16. **Incremental-information analysis uses block-wise OLS R² increments via numpy least-squares, not a formal nested-model-comparison framework (e.g. likelihood-ratio tests) or true conditional mutual information.** Consistent with Phase 1B's no-`statsmodels` precedent (still not installed) and the charter's own explicit list of acceptable methods ("incremental variance explained... or other scientifically justified methods"). Explicitly framed as variance bookkeeping, not predictive modeling, per the charter's governing philosophy for this phase ("do not optimize for prediction").

17. **Redundancy is measured via Pearson correlation among family-representative scalar metrics (one per family), not a full covariance/factor-analytic treatment of every column.** A representative-metric approach was chosen for tractability and interpretability (a 10x10 correlation matrix is directly readable; a full multi-column covariance structure across ~20 raw fields would not be, and the charter asks for family-level redundancy, not column-level).

18. **The tracked-population minimum-volume thresholds (≥100 tracked pitches, ≥15 batted balls) are reused from Phase 1B's established viable-population logic, not re-derived.** Keeps the population comparable across phases rather than introducing a new, unexplained threshold.

19. **`reports/phase1c/` and `scripts/phase1c/` subdirectories**, same rationale as Phase 1B's #13 — keeps three phases' outputs cleanly separable.

## Engineering Charter (architecture freeze, interface specification, Module 1 readiness)

20. **`reports/engineering/`, no accompanying `scripts/engineering/`.** This charter is pure specification — no new data, no new statistical computation — so, unlike every prior phase, there's no new pipeline code to house; all 13 deliverables are markdown, referencing already-existing pilot scripts (`scripts/`, `scripts/phase1b/`, `scripts/phase1c/`) rather than adding new ones.

21. **Stuff+ reconciliation was resolved as a precise hybrid (augment where `stuff_plus_aaa` operates in AAA, extend independently into tracked Low-A) rather than picking a single option from the charter's A-E list wholesale.** The evidence didn't cleanly support any single option — `stuff_plus_aaa` and Module 1 don't estimate the same construct (no shared target/label), but their raw physical-feature inputs substantially overlap, and Module 1's reliability (0.91-0.99) dramatically exceeds `stuff_plus_aaa`'s pitcher-level stability (0.28) on those same inputs. Forcing a single-letter answer would have either overclaimed (replace/become) or underclaimed (leave unchanged) what the evidence actually supports.

22. **Module 1's readiness verdict is split by integration path, not given as one GO/NO-GO.** The independent pipeline (own data source, new PROSPX card field) and the `stuff_plus_aaa`-augmentation path have genuinely different blockers — the former has none, the latter is blocked on reconciling two different public data endpoints (MLB Stats API feed vs. Baseball Savant `statcast-search-minors`). A single verdict would have misrepresented one path or the other.

23. **Modules 2 (Arsenal Construction) and 4 (Ground-Ball Tendency) ship with no confidence/reliability field in their interface specification, by design, not omission.** Their own-metric reliability has never been tested (only their relationship to other modules was, in Phase 1C) — per this charter's engineering standard ("no undocumented transformations," "explicit reliability"), fabricating a confidence field without evidence would violate the standard the charter itself sets. The schema is designed to accept the field once evidence exists (an additive, MINOR version change), not to pretend it exists today.

24. **This charter's engineering standards are proposed for repo-wide adoption but not enacted repo-wide.** `eephus.io` has no root-level `CLAUDE.md`/`AGENTS.md` for a research charter to amend, and doing so unilaterally would exceed this charter's authority. `ENGINEERING_STANDARDS.md` is written ready-to-adopt, with this limitation stated explicitly rather than silently overreaching.

25. **The final ruling states plainly that this charter does not fully pass its own acceptance criteria** (no module has a *built* consumer yet — only designed ones) rather than reinterpreting the criteria to produce a passing result. Four charters of documentation and specification work is real progress, but it is not the same thing as a shipped module, and the ledger records that distinction rather than blurring it.
